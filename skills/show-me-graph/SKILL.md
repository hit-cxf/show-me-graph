# Show Me Graph

Use this skill when a user asks you to investigate a paper or research question, explain a graph claim, or change the Show Me Graph knowledge base. The browser UI and this skill are clients of **one local service**; write through the HTTP API, never by editing the service's JSON, SQLite, source corpus, or browser storage. A `SKILL.md` file is an operating guide, not a background research daemon.

The bundled `scripts/smg.py` is a Python 3 standard-library client. It uses `SMG_BASE_URL` or `http://127.0.0.1:4317` and prints JSON. Use the host's HTTP tool instead if shell execution is unavailable. No vendor-specific agent feature is required. Read [references/api.md](references/api.md) when you need record shapes and commands; read [references/research.md](references/research.md) for literature extraction, provenance, and fast/deep mode.

## Start from the live state

1. Call `python3 <this-skill-dir>/scripts/smg.py health`, then `snapshot`. Check the revision, `preferences.maintenance_prompt`, existing identities, selected papers, and whether the service permits writes. Read and apply these saved preferences at the start of every maintenance task, including its research scope, searches, extraction, notes, and presentation. An empty prompt adds no preferences. A read-only M0 server cannot fulfill edit requests; report that limitation instead of editing files behind it.
2. Reuse existing paper, entity, and evidence IDs. Check the local graph before searching elsewhere; normalize DOI/arXiv ID and version before adding a paper. A mention of another work in a PDF is not proof that the current system *uses* its method.
3. Immediately before submitting edits, reread the snapshot and compare its preferences and revision with those used to prepare the result. If preferences changed, revise the pending work accordingly; reconcile any record changes, then send the latest revision with `--if-match` or `expected_revision` in an atomic batch. If a 409 conflict occurs, reread and reconcile again instead of blindly replaying writes.
4. After a successful write, read the affected record or snapshot and give the user the changed IDs, evidence state, and any gaps. The UI receives the same stored revision; no manual browser refresh or separate copy is part of the workflow.

Saved preferences override this skill's default workflow choices, such as collection scope, organization, and recording style; the user's current explicit instructions take priority over both. Preferences do not establish academic facts, waive evidence validation, or grant extra permission to send external messages or delete data. Change the saved prompt only when the user asks to change preferences, through `preferences --file ... --if-match ...`; do not write inferred preferences back automatically. These instructions apply when an Agent loads this skill; saving a prompt does not start a background Agent or enforce compliance in third-party Agents that have not loaded it.

## Research and graph updates

For **fast** mode, answer the user's specific reading question from existing graph evidence, then inspect only the missing original passages and necessary cited work. Stop when the question is supported or remaining gaps are explicit. For **deep** mode, define the supplied anchor and a finite coverage plan, then systematically extract the paper's systems, methods, components, definitions, benchmarks, findings, implementation choices, and limitations. Trace important references and compare alternative branches within that scope. The user's two sample questions about activation and VAE compression are examples, not a restriction on coverage. Record completed and unresolved topics; do not equate a finite survey with every paper in an entire field.

Before creating or revising a technical slice, analyze the source's logical relationships, containment, dependencies, and sequence, then choose the visual arrangement. Record these as distinct typed relations through the API: containment such as `has_component` or `has_stage` may define parent/child branches; `uses`, `trained_with`, and evaluation relations express dependencies; `precedes` orders peers without nesting them; `reports`, `mitigates`, and `qualifies` express claims and reasoning alongside the structure. Review proposed parents, ordering cycles, and evidence before drawing. Never invent or reinterpret a relation to produce a prettier tree, and do not present an arbitrary layout forest as the paper's academic hierarchy. Read the [semantic graph protocol and examples](references/research.md#analyze-relationships-before-drawing) before extracting or restructuring these relationships.

Represent each distinct result as an entity associated with its paper. Reuse one canonical identity for a genuinely shared method across papers, while keeping every displayed occurrence named; do not duplicate identities or suppress labels to simplify the drawing. Preserve isolated nodes when the source provides no sound edge. A paper-level citation and a method-level adoption are different claims. Cross-paper technique relationships need their own evidence or must be marked as inferences.

By default, submit valid findings to the main graph immediately, including AI inferences; follow a different collection workflow when the user or saved preferences specify one. Preserve `basis` and source IDs, make unverified/missing evidence explicit, and keep contradictory reports in `conflicts` and rejected edges in `negative_examples`. Do not silently overwrite a user's correction. Local PDF evidence must identify a fixed paper version, hash, page, quote, and, when available, coordinates. Use `locate <evidence-id>` to validate the stored anchor before saying a claim is traceable to the original PDF. If the underlying passage cannot be verified, describe the claim as unresolved rather than inventing a citation.

## Everyday maintenance

Use the same API for edits a person makes in the WebUI: create or update paper/entity/relation records; add notes to paper, entity, relation, or evidence IDs; create tags and add their IDs to records; create groups and update their paper membership; set the shared selected papers and active group with `state`; read user preferences with `get-preferences`; and retrieve evidence. For interdependent changes, use a single `batch`. Consult [references/api.md](references/api.md) before deleting or changing IDs, because other records may reference them.

The current API is a local knowledge-base editing surface. It does **not** itself search the web, parse new PDFs, schedule a deep task, or write to Zotero. Perform supported research with the host agent's tools and import results through this API. If a requested action has no implemented endpoint, state the exact gap rather than claiming it happened. In particular, Zotero auto-collection requires a configured target collection and a working Zotero write connector; this Skill alone cannot perform or verify it.
